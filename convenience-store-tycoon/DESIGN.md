## 0. 语言假设与技术选型说明（明确声明）

**假设：使用 Python 3.10+ 实现，仅依赖标准库，零第三方依赖。**

理由：

1. **用户未指定语言**，需自行选择并声明。选择 Python 的依据：
   - 本项目是**回合制、以数值仿真为核心**的游戏，开发重心在规则建模与平衡，而非性能；Python 的开发效率最优。
   - 标准库已完整覆盖需求：`json`（存档）、`random`（可播种、可序列化的随机）、`dataclasses`（数据模型）、`enum`（状态机）、`argparse`（命令行参数）、`pathlib`（跨平台路径）。
   - **零依赖**意味着 `python main.py` 即可运行，无安装摩擦，符合"终端运行、纯文本"的轻量定位。
2. **备选方案对比**：
   - Go / Rust：单文件分发好，但对本项目而言编译工具链是无谓成本；
   - C# / Java：需要运行时环境，终端文本渲染无优势；
   - Node.js：同样可行，但 `dataclasses` + 枚举 + 类型标注在建模规则系统时表达力更直接。
3. **平台兼容要点**（写入第二阶段 README）：Windows 终端需在入口处执行
   `sys.stdout.reconfigure(encoding="utf-8")` 并启用 VT 转义序列；同时提供 `--ascii`
   启动参数，在老旧终端下将界面降级为纯 ASCII 字符，不使用制表符/Emoji。
4. 性能预估：日仿真为每秒 200~600 名虚拟顾客 × 每人 ≤10 次决策，单日 <0.5s，
   无需考虑性能优化（如 NumPy/C 扩展）。

## 1. 核心游戏循环

### 1.1 一句话概括

玩家每日循环执行：**晨间准备（进货 → 定价 → 陈列 → 促销）→ 营业（顾客自动涌入并决策，玩家处理客服事件）→ 打烊结算（损益、KPI、声誉）→ 夜间运营（报表 → 扩张投资 → 贷款 → 存档）**，用利润滚动扩大门店规模，在限定天数内达成净资产目标即胜利；现金枯竭且无法融资即破产。

### 1.2 每日流程图（文字版）

```
┌─────────────────────────── 新的一天 (Day N) ───────────────────────────┐
│                                                                        │
│  [晨间准备 DAY_PREP]（玩家主导，可反复进出子界面）                        │
│   1. 查看晨报：昨日摘要 + 今日事件/天气/日历提示                          │
│   2. 进货：向供应商下订单 ──→ 当日早到货（标准）/ 次日到货（低价供应商）    │
│   3. 定价：为每个上架商品设定售价（改动即时生效）                          │
│   4. 陈列：仓库批次 → 货架槽位（黄金位/普通位），清理过期批次              │
│   5. 促销：设置折扣/临期清仓（持续 N 天）                                 │
│   6. 其他：雇员排班（后期）、设备维护                                    │
│            │                                                            │
│            ▼  玩家确认"开门营业"                                         │
│  [营业模拟 DAY_OPEN]（系统自动推演，玩家可旁观/加速）                     │
│   for 时段 in 08:00..24:00（16 个小时刻度）:                             │
│      a. 顾客到达：客流引擎按"路过人流 × 进店率"生成顾客                   │
│      b. 顾客 AI：进店 → 逐项购物决策 → 排队 → 结账/放弃                   │
│      c. 客服事件：排队过长/投诉弹出选择框（安抚/快速通道/忽略）            │
│      d. 实时摘要滚动：客流、营收、缺货、满意度变化                        │
│            │                                                            │
│            ▼  24:00 自动打烊                                             │
│  [每日结算 DAY_SETTLE]（纯计算，无输入）                                 │
│   损益表：营收 − 售出成本 − 报废损失 − 房租/水电/工资 − 利息 ± 事件        │
│   库存：批次 +1 天保质期；过期批次下架报废                                │
│   客群：满意度均值 → 声望增减；忠诚度按顾客是否满意更新                    │
│   KPI：客流量/转化率/客单价/周转率/缺货率/报废率 → 写入 30 日滚动账本      │
│            │                                                            │
│            ▼                                                            │
│  [夜间运营 NIGHT]（玩家主导）                                            │
│   1. 报表与图表（文本柱状图、KPI 趋势）                                   │
│   2. 扩张投资：店铺升级 Lv1→Lv5 / 设备购置（冷柜等）/ 雇员招聘             │
│   3. 财务：贷款 / 还款 / 查看信用额度                                     │
│   4. 破产判定：现金 < 0 且超出信用额度 → GAME_OVER                        │
│   5. 自动存档（每日 1 个滚动槽）+ 玩家手动存档                            │
│            │                                                            │
└────────────┴──→ Day N+1 回到 [晨间准备]；达胜利条件 → VICTORY             ┘
```

## 2. 游戏系统

### 2.1 运营 KPI 与计算公式

所有 KPI 每日结算时计算一次，滚动保留近 30 日账本；夜间报表可绘制趋势。

| KPI | 计算公式 | 健康区间 | 用途 |
|---|---|---|---|
| 营收 Revenue | `Σ(成交单价 × 成交数量)` | 随规模增长 | 损益表第一行 |
| 毛利 GrossProfit | `Σ(售价 − 售出批次进价) × 数量` | 毛利率 28%~38% | 经营核心 |
| 净利 NetProfit | `毛利 − 报废损失 − 房租 − 水电 − 工资 − 利息 − 事件支出 + 事件收入` | > 0 且逐月抬升 | 扩张能力 |
| 客流量 Traffic | 当日进店人数 | Lv1 约 110~170 | 规模指标 |
| 进店率 EnterRate | `进店人数 / 路过人数` | 0.26~0.40 | 门店吸引力 |
| 转化率 Conversion | `成交顾客数 / 进店顾客数` | ≥ 0.72 | 选品与定价合理性 |
| 客单价 AOV | `营收 / 成交单数` | ¥14~¥20 | 连带销售 |
| 库存周转率(日) | `当日售出成本 / ((期初库存成本+期末库存成本)/2)` | 0.25~0.5（即 2~4 天一转） | 资金效率 |
| 库存周转天数 DOH | `1 / 周转率` | 2~4 天 | 同上 |
| 缺货率 OOSRate | `缺货需求次数 / 总需求次数` | < 8% | 服务水平 |
| 报废率 WasteRate | `报废批次成本 / 近 7 日累计进货成本` | < 4% | 订货准确度 |
| 满意度 Satisfaction | 每位成交顾客产生满意度增量（见 §3.2），取当日均值 | 65~85 | 声望输入 |
| 声望 Reputation | `R' = clamp(R + 0.18 × (满意度均值 − 65), 0, 100)`，显式 ★★★☆☆ | 55~90 | 客流乘数、贷款门槛 |

> 报表页对以上指标给出"今日 / 7 日均值 / 30 日趋势"三列，并用文本柱状图渲染近 14 日营收与净利。

### 2.2 顾客 AI 决策逻辑

#### 2.2.1 顾客原型（Archetype，配置于 `config/customers.py`）

| 原型 | 流量占比 | 主要时段 | 预算(¥) | 价格敏感 | 典型购物篮 | 耐心(排队人数) |
|---|---|---|---|---|---|---|
| 上班族 | 30% | 7-9, 11-13, 17-19 | 18~26 | 0.35 | 咖啡、便当、瓶装饮料 | 4~6 |
| 学生 | 20% | 15-19 | 10~18 | 0.60 | 零食、饮料、冰淇淋 | 3~5 |
| 家庭主妇/主夫 | 18% | 9-11, 16-18 | 25~60 | 0.50 | 粮油、日用品、生鲜 | 5~8 |
| 夜猫子 | 12% | 21-24 | 12~25 | 0.30 | 泡面、啤酒、熟食 | 2~4 |
| 银发族 | 12% | 6-10 | 8~20 | 0.75 | 早餐、牛奶、报纸 | 6~9 |
| 过路客 | 8% | 全时段 | 5~15 | 0.40 | 瓶装水、应急品 | 1~2 |

每位顾客在生成时按原型随机化：预算、耐心、`WTP 浮动 ±12%`、2~4 个"今日需求"（从原型偏好品类加权抽取）、忠诚度初值（过路客恒为 0）。

#### 2.2.2 决策管线（伪代码）

```
function decide_arrival(customer, store, context):        # 每小时刻度
    p = archetype.traffic_weight[hour]                    # 原型时段权重
    p *= store_attractiveness(store)                      # 声望/陈列/促销合成, 见下
    p *= context.traffic_modifier                         # 天气/事件/难度
    p *= (0.55 + 0.45 * customer.loyalty)                 # 忠诚回头加成
    arrive if rand() < p_normalized

function store_attractiveness(store):
    return 0.40*norm(store.reputation)                    # 声望
         + 0.25*norm(store.display_index)                 # 陈列满架率+黄金位利用率
         + 0.20*norm(store.promo_strength)                # 在促商品力度
         + 0.15*norm(store.assortment)                    # 在售品类数/解锁品类数

for need in customer.needs:                               # 逐需求决策
    candidates = shelf_items_of_category(need.category)   # 只看货架, 仓库不可见
    if not candidates:
        record_oos(need); try_substitute(other_category)  # 替代成功率 0.35
        continue
    best = argmax over candidates of utility(item, customer):
        utility = 0.45*price_score + 0.20*position_score
                + 0.20*promo_score  + 0.15*stock_score      # 权重可配
        price_score   = sigmoid(k * (wtp/item.price - 1))   # wtp=参考价×个人浮动
        position_score= 1.0 黄金位 / 0.6 普通位
        promo_score   = 1 + promo_depth × archetype.promo_sensitivity
        stock_score   = 余量充足 1.0 / 零散 0.7
    if utility >= BUY_THRESHOLD(0.5) and 购物篮合计+price <= budget:
        cart.add(item, qty=1..2)                          # 大件概率 0.25 加第二件
    else:
        record_skipped(need)

if cart and queue_len(customer) > customer.patience:       # 排队判定
    abandon_cart(); satisfaction -= 6; record_abandon()
else:
    pay(cart); satisfaction_delta = 2
        - 4*price_unfairness(price/ref_price)             # 定价>参考价×1.25 扣分
        - 3*oos_encountered - queue_penalty
    loyalty += 0.04 * sign(satisfaction_delta) 且向 [0,1] 衰减收敛
```

#### 2.2.4 缺货惩罚规则

缺货发生时（顾客有需求但货架无货）：该需求计入**缺货率**；若无替代 → 顾客满意度 −3；同一顾客当日第 2 次缺货 → 忠诚度 −0.02；缺货率连续 3 日 > 15% → 触发"口碑受损"事件（声望 −4）。缺货**不产生直接罚款**，通过客流与转化间接施压——这是刻意设计，避免惩罚感过重。

#### 2.3.2 批次（Batch）与保质期

- 库存以**批次**记录：`(批次号, 进货日, 到期日, 数量, 进价)`；仓库与货架共用同一批次池，售出按 **FIFO** 扣减（先进先出，保证旧批次先卖）。
- 每日结算时所有批次"年龄 +1 天"；`剩余保质期 ≤ 阈值(默认 2 天)` 的批次在晨间**高亮提示**并建议临期促销；`剩余 ≤ 0` 自动下架，按批次进价计入**报废损失**。
- 保质期极短商品（当日售罄型，如现磨咖啡）不进批次池，按"当日产能"模型处理（晨间设定备量，打烊未售即全损）。

#### 2.3.3 补货机制

- 晨间下单，**标准供应商当日早到货**；**低价供应商（进价 −6%）次日到货**，需预测明日需求——风险与折扣的取舍。
- 单次订货上限 = `min(仓库剩余容量, 现金可支付量, 供应商单品上限)`；按箱规整箱进货。
- 建议订货量辅助：界面显示"近 7 日日均销量 × 目标覆盖天数(2 天) − 现有量"，仅供参考，不强制。

#### 2.3.4 缺货、滞销与清仓

| 情形 | 判定 | 玩家可执行的处理 |
|---|---|---|
| 缺货 | 货架余量 0 且有需求 | 下单补货；长期缺货触发 §2.2.4 惩罚链 |
| 滞销 | `库存持有天数 / 该品类目标周转天数 > 1.5` | 降价（改售价）、限时折扣、丢弃（沉没成本） |
| 临期 | `剩余保质期 ≤ 2 天` | 临期区半价（促销位）、员工内购回收 50% 成本（一次性） |
| 过期 | 结算时自动处理 | 无（只能预防），报废损失计入当日损益 |

### 2.4 经济系统与难度曲线

#### 2.4.1 单日经济模型（普通难度，Lv1，经营得当的期望值）

| 项目 | 金额(¥) | 备注 |
|---|---|---|
| 营收 | ≈ 1,800 | 138 进店 × 78% 转化 × ¥16.5 客单 |
| 售出成本 | ≈ −1,224 | 毛利率 32% |
| **毛利** | ≈ 576 | |
| 房租 | −400 | Lv1 |
| 水电 | −96 | 60 + 营收×2% |
| **净利** | **≈ +80** | 经营不善（缺货多/定价失误/报废高）为负 |

设计意图：**首周净利在 0~±200 区间徘徊**，逼迫玩家优化（黄金位陈列、控报废、精准订货）；声望从 60 → 80 后客流 ×1.3~1.5，净利可达 ¥400~700/日，形成正反馈；每次升级都是"花大钱买更高客流上限"的风险决策。

#### 2.4.2 店铺等级（升级在夜间执行，即时生效次日客流）

| 等级 | 升级费用 | 声望门槛 | 货架槽/容量 | 仓库 | 解锁 | 客流乘数 |
|---|---|---|---|---|---|---|
| Lv1（初始） | — | — | 6 / 30 | 300 | 常温 12 品类 | ×1.00 |
| Lv2 | ¥10,000 | ≥55 | 10 / 30 | 600 | +8 品类（含冷藏类） | ×1.30 |
| Lv3 | ¥25,000 | ≥65 | 16 / 34 | 1,200 | 冷柜设备可购（解锁鲜食） | ×1.25 |
| Lv4 | ¥60,000 | ≥72 | 24 / 36 | 2,200 | 24h 营业开关、雇员 2 名 | ×1.20 |
| Lv5 | ¥120,000 | ≥80 | 32 / 40 | 4,000 | "连锁筹备"（多店接口启用提示） | ×1.15 |

#### 2.4.3 贷款与信用

- 信用额度 = `max(0, 净资产 × 0.5 − 未偿贷款)`，且要求声望 ≥ 40；日利率 0.3%，按日计息，到期（30 天）自动扣还本息，现金不足则转为逾期（每日声望 −2）。

#### 2.4.4 难度曲线（开局选择，写入存档）

| 难度 | 初始资金 | 客流乘数 | 房租乘数 | 恶性事件强度 | 胜利净资产(90 天) |
|---|---|---|---|---|---|
| 轻松 | ¥25,000 | ×1.30 | ×0.85 | ×0.6 | ¥150,000 |
| 普通 | ¥20,000 | ×1.00 | ×1.00 | ×1.0 | ¥200,000 |
| 硬核 | ¥15,000 | ×0.85 | ×1.25 | ×1.4 | ¥260,000 |

节奏设计：第 1~10 天生存期（学会不亏）→ 11~30 天优化期（净利转正并积累）→ 31~90 天扩张期（升级/设备/雇员组合拳）。90 天未达标不判负，转为"无尽模式"继续经营，胜利画面改为成就结算。

#### 2.4.5 破产判定

夜间结算后检查：`现金 < 0` 时若 `信用额度 > 0` 自动触发紧急贷款（金额补足到 0，声望 −3 并弹提示）；若 `现金 < 0 且信用额度 ≤ 0` → **GAME_OVER**，展示生涯统计后返回主菜单。

### 2.5 随机事件系统

#### 2.5.1 引擎规则

- **触发时机**：每日晨间准备前掷骰；每个事件独立判定 `rand() < 基础概率 × 难度系数`，并受**冷却天数**与**前置条件**约束（最多同时生效 3 个修饰型事件）。
- **效果载体**：修饰型（TrafficModifier / CostModifier / DemandShift，带持续天数）与一次性型（现金增减、库存损耗、声望增减）。
- **配置驱动**：事件表为纯数据（`config/events.py`），新增事件不改引擎代码。
- **公平性**：连续恶性事件次数 ≥ 2 时，下一次恶性事件概率 ×0.5（怜悯机制，参数可调）。

### 4.2 核心数据模型（dataclass 草案）

```python

@dataclass

    item_id: str | None; batch_alloc: dict[int, int]  # 批次→数量

@dataclass
class Store:
    level: int; cash: float; reputation: float      # 0~100
    warehouse: list[Batch]; shelf_slots: list[ShelfSlot]
    prices: dict[str, float]; promos: dict[str, Promo]
    equipment: set[str]; employees: list[Employee]
    loans: list[Loan]; orders_in_transit: list[Order]

@dataclass
class Customer:
    archetype: ArchetypeId; budget: float; patience: int
    wtp_jitter: float; loyalty: float
    needs: list[Need]                  # (category, qty)

@dataclass
class DayReport:                  # 结算系统纯函数的输出, UI 只读渲染
    day: int; revenue: float; cogs: float; spoilage: float
    fixed_costs: dict[str, float]; interest: float
    event_effects: list[str]; net_profit: float
    traffic: int; conversions: int; aov: float
    oos_rate: float; turnover: float; waste_rate: float
    satisfaction_avg: float; reputation_delta: float
```

### 4.3 模块划分原则（单向依赖）

```
main → ui → core → config        (config 被所有人读, 不依赖任何人)
save → core                       (只序列化 core 数据模型)
tests → core (+ui 白盒少量)
```

- **core 零 IO**：`core/` 任何模块不得 `print` / `input`；模拟器产出 `DayLog`（逐事件流水）与 `Prompt`（需要玩家干预的客服事件队列），由 UI 决定呈现与收集应答，应答再回注模拟器——这同时为 §5 的多人/回放预留了指令化边界。
- **结算纯函数**：`settle(state, day_log) → (new_state, DayReport)`，无副作用、可单测、可回放校验。
- **仿真与显示严格分离**：UI 层只做"取数 → 格式化 → 收输入"，不允许出现任何游戏规则判断（如"是否过期"），保证换 UI（如未来 Web 版）不动规则。

### 4.4 存档格式与版本兼容

- **格式**：JSON（UTF-8），顶层结构：

```json
{
  "format_version": 1,
  "app_version": "0.1.0",
  "created_at": "2026-10-03T21:40:00",
  "difficulty": "normal",
  "rng_state": [3, (tuple→list), null, ...],
  "game": { "day": 12, "store": {...}, "ledger": [...] }
}
```

- **序列化策略**：每个核心模型显式实现 `to_save() / from_save()`（不用反射魔法，字段改名不静默破坏旧档）；`rng_state` 一并保存，保证"读档后随机序列可复现"，为回放与调试服务。
- **版本兼容**：加载时比对 `format_version`：
  - 相同 → 直接载入；
  - 存档版本更旧 → 沿注册的迁移链 `MIGRATIONS: dict[int, Callable[dict, dict]]` 逐级升级（如 `1→2` 给存量商品补默认字段），迁移前先备份原文件为 `.bak`；
  - 存档版本更新 → 拒绝加载并明确提示"请升级游戏"，绝不猜测。
- **写入策略**：临时文件 + `os.replace()` 原子替换，避免断电损坏；自动存档（每日结算后滚动覆盖）+ 3 个手动槽。
- **数据裁剪**：账本只保留近 30 日明细与全历史日汇总（日粒度 5 个聚合数），控制存档体积。

### 4.5 配置集中与"禁止魔法数字"的落实方式

1. 全部数值常量进 `config/`，按域分文件；每个常量带注释（默认值、单位、调节方向的影响）。
2. `core/` 中只允许引用 `config` 符号与已存字段，PR 级自查规则：`grep -nE "[0-9]+\.[0-9]+|[^_0-9][0-9]{2,}" core/` 仅允许索引、枚举序号、0/1/-1。
3. `tests/test_no_magic_numbers.py` 以静态扫描做回归护栏（第二阶段实现）。
4. README 附"可调参数表"（名称、默认值、作用、调节后果），与本文档 §2 各参数表同源。

## 5. 可扩展性设计（仅描述，不实现）

> 当前单店单玩家，但以下抽象点在第一阶段即写入架构，避免第二阶段返工。

### 5.1 多门店 / 连锁

- **所有权上移**：引入 `Company`（玩家公司）实体，持有 `stores: dict[StoreId, Store]`；`Game` 持有 `Company` 而非直接持有 `Store`。存档顶层预留 `"company"` 节点。
- **共享与隔离**：`Reputation` 拆为 `BrandReputation`（连锁共享）与 `StoreReputation`（单店），客流合成时加权——接口现在就按两个来源设计参数。
- **供应链抽象**：`Supplier` 从"目录查表"升级为对象（报价、起订量、配送半径/延迟、合约折扣）；连锁可解锁"集中采购合约"（按总订量阶梯价）与"配送中心 DC"（`Warehouse` 基类派生 `StoreWarehouse / CentralWarehouse`，调拨单 = 跨仓批次转移）。
- **经理自动化**：`PricingPolicy / OrderingPolicy`（策略对象）挂到店上，玩家离店时由策略代管——单店后期"雇佣店长"即此机制的首次落地，多店时复用。

### 5.2 多人模式（回合制/异步）

- **指令化交互**：所有玩家操作统一为 `Command`（`validate(state) / apply(state) / to_wire()`），晨间准备即"提交一串指令"；单机路径 = 本地输入直接 apply，多人路径 = 指令序列化后经传输层交换。`ui` 只产出 `Command`，天然满足。
- **输入源抽象**：`InputSource` 接口（本地终端实现为第一版）；热座/联机只需替换实现。
- **确定性内核**：随机全部经 `rng.py` 封装且状态随存档序列化 → 各端同指令序列必得同结果，支持"指令日志回放"式同步与断线重连，无需锁步传输全部状态。
- **异步节奏**：日为单位结算（现有状态机天然按日分帧），适合"每日一回合"的异步多人。

### 5.3 其他预留

- **事件总线**：核心系统间通过显式调用，但 `DayLog` 已是事实上的事件流；未来 `EventBus` 直接以 `DayLog` 条目为消息原型。
- **Mod 友好**：商品/事件/顾客原型全部为纯数据表，加载时可合并外部 JSON（版本字段一并校验），引擎零改动。
